# 轻量级 AI 软件交付协议 V1.6

来源：Long《轻量级 AI 软件开发标准化工作流 V1.6》，2026-09-18 定版；本仓库是其可安装实现。包版本与协议版本分别维护。本页保留核心规则，文末明确实现约定。

## 1. 主链与边界

`Request → Contract → Graph → Execute → Verify → Delivery → Done`

正式 Verify 失败 → 诊断根因 → 在额度内修复/局部 Replan → 再 Verify。普通修复返回 Execute，实质 Replan 返回 Graph，必要决策进入 Human Gate。条件不足记 BLOCKED，条件恢复后继续，不自动判失败或超时取消。

适用于本地/测试环境的软件需求、缺陷与交付。首版不涉及生产运维，不建设动态 DAG、能力平台、事件总线、复杂记忆服务、多 Agent Supervisor、并发锁系统或全量可观测平台。

## 2. Contract、Graph 与 Impact

Contract 必含：目标和交付形态；范围/非范围与兼容边界；业务语义、环境和权限；AC 编号、Required/Conditional/Optional 与必要证据；LOW/NORMAL/HIGH 风险；根因修复、任务总修复和有效执行时间上限；Human Gate 条件及客户确认是否必需。风险不清按更高一档处理。

Graph 从一个可验收纵向切片开始。编号清单足够，每步写“动作 → 输出 → 检查”；只对真实依赖画图。复用现有实现和检查入口，低风险不补造测试体系。

Impact 必查五类影响：

| 维度 | 内容 |
| --- | --- |
| Direct | 直接改动的模块与入口 |
| Callers | 调用方、消费者、上下游 |
| Data | 数据、事务、缓存、状态和兼容 |
| External | 外部服务、消息、配置和权限 |
| Regression | 旧行为与必要回归 |

未知项补查链路，不能直接 N/A。必要任务集合或执行路径实质改变，或 Impact 的任一维度需要实质改写，才算 Replan；改措辞、补细节不算。实质 Replan 最多 1 次。

## 3. 能力与角色

按当前任务加载 Skills/SOP、源码搜索、构建、测试、浏览器、数据库只读等能力；Provider 可替换，AC 口径不变。例如 CodeGraph 缺失可以用 `rg` 和源码追踪替代。只有 Required 能力无等价替代才 BLOCKED。

Builder 可读写、构建和本地测试；不改验收语义，不拥有标准路径的最终 PASS 权限。Verifier 默认读、测、只读 DB、日志和 HTTP；可在隔离位置写测试/复现脚本，不改业务代码。角色约定不等于操作系统或工具的硬权限隔离。

交接包包含 Contract/AC、Graph/Impact、当前产物/Diff、构建运行入口、环境/测试数据、已知问题与原始 Evidence。交接内容分区，保证 Verifier 可以先做 Phase A 再读实现材料。

## 4. 独立验证

标准路径使用独立上下文，避免继承 Builder 的完成结论。

1. Phase A：只看 Contract/AC/Impact，先固定黑盒场景与预期。
2. Phase B：再看代码/Diff，补充事务、缓存、并发、异常等实现特有风险。
3. 实际执行并记录 Evidence，逐 AC 下结论。

本地自检不能自动替代独立验证。没有可用独立上下文时，保留 NOT_VERIFIED 或因能力受阻的 BLOCKED，并交付候选产物与交接材料。

Fast Verify 例外必须**同时**满足：LOW 风险；不改可执行逻辑、数据、配置、权限或 API；不涉及金额、状态或跨模块；Diff 可以直接审查。仅标 LOW 不够。任一反例出现就恢复标准隔离。

## 5. Evidence 与结论

每条证据含：AC 编号、实际产物标识、环境与输入、实际命令/操作、真实结果、原始报告位置。共用批次只记一次，由 AC 引用。

产物标识不能只写 HEAD：未提交时需附包含已跟踪变更、未跟踪新增及删除文件的清单和 Diff/校验值。不能把 `git diff` 没包含的新增文件当作已记录。报告不要包含密钥、客户完整资料或敏感生产日志。

AC 的 `type`、当前 `applicability` 与 `verdict` 分开记录，详细机器字段见 [Task Record schema](task-record-schema.md)。

| 结论 | 含义 |
| --- | --- |
| PASS | 已执行且满足预期，证据对当前产物有效 |
| FAIL | 已执行，实际结果不满足预期 |
| NOT_VERIFIED | 尚无有效执行证据，包括跳过 Required |
| BLOCKED | 环境、权限或依赖等使必要动作无法继续 |
| N/A | 执行该 AC 前已有依据确认本任务实例不适用；记录理由和依据，不是失败后的豁免 |

适用的 Required 必须 PASS。Required 若在该 AC 执行前有依据确认不适用，可以记录 `NOT_APPLICABLE + N/A`；条件未知不能自行标不适用。Conditional 的触发状态必须与适用性一致，触发后按 Required 验收。Optional 跳过不否定必要项，但其 FAIL、BLOCKED 或 NOT_VERIFIED 仍需披露。相关代码、配置、数据、测试或 AC 语义变化后，受影响旧结论待复核；原始证据足够则重新判定，不足则补测。

按任务选必要检查：UI 需要真实操作、边界输入和错误提示；业务逻辑检查分支、数量/金额、幂等与旧行为；数据变更检查隔离环境、事务回滚和兼容；权限/跨层链路检查合法与越权身份、完整路径和数据范围。构建通过本身不能证明全部行为正确。

## 6. 受控修复与 Human Gate

正式 Verify FAIL 先分类：实现问题返回 Execute；计划不足先补查 Impact，实质改变进入 Replan；测试/数据问题需证明问题确在输入，不能降低 AC；环境/权限不足 BLOCKED；业务语义、范围或 AC 变更需要必要决策。

- 同根因第 1 次失败：原 Builder 修复 → Verify。
- 同根因第 2 次失败：必要时 Context Reset，由新上下文完成第 2 次修复 → Verify。
- 再次失败：停止自动修复，Human Gate。
- 换根因不清零任务总修复数；总次数或 T 到限停止新自动动作。
- 恢复、Reset、换模型、换上下文均不重置累计值。

Context Reset 只在重复失误、关键证据冲突、旧假设污染或明显混乱时触发。保留 Contract、当前产物、已执行 Evidence、失败根因、剩余额度与必要项目事实，不把全部历史解释重新注入。

Human Gate 四类：H1 关键业务语义不清；H2 改变已确认范围、兼容或 AC；H3 不可逆、支付退款、生产数据等必要授权；H4 额度耗尽或关键证据冲突。已经授权的普通可逆工作继续，不把每步都变成审批。

等待时记录原因、最小所需输入、恢复条件与剩余额度。恢复依次核对 Contract、产物和 Evidence、额度，再从受阻阶段继续。DONE/FAILED/CANCELLED 为终态；Human Gate/BLOCKED 不是终态。

## 7. 一份任务记录与时间

记录 Contract、Graph、Impact、Evidence、Delivery、Knowledge Sync；Loop/Exception 只在失败、阻塞、Replan、Reset 时追加。不为格式预建无用文档或反复填写空 N/A。v0.2.0 的任务 Markdown 内含一个版本化 JSON 机器区，作为状态、计数和 Evidence 引用的机械来源；正文保存判断依据与可复现细节，不建立第二套数据库。

有效执行时间 T 从 Contract 确认后的首个分析动作起，到 Delivery 和必需 Knowledge Sync 完成止。包含分析、实现、自检、Verify、修复、交付整理和必需知识更新；不包含 Human Gate/BLOCKED 等待与用户主动暂停。使用粗粒度执行片段即可；记录实际起止和累计，不伪造精确计时。

## 8. 交付、知识同步和 DONE

交付四部分：Artifact（代码/文件、标识、范围、Diff、限制）；Reproduce（环境、构建运行、初始化、测试数据）；Acceptance（逐项结果与证据）；Knowledge Sync（状态、来源、文档）。

API、Schema、模块依赖、核心业务规则、状态机、关键调用链/MQ、架构决策或运行条件变化时同步项目知识，优先更新现有文档。

| 来源 | 能证明什么 |
| --- | --- |
| 已确认 Contract / 决策 | 目标与约束，不能证明已经实现 |
| 源码 / Diff / Schema | 特定版本静态定义，不能证明某环境已应用 |
| 运行 Evidence | 特定产物、环境、输入、操作下的行为，不能外推全部环境 |

同步结论为“已更新并回读”“已查无增量并记录理由”或“同步失败”。无增量不重复改正文/日期。同步失败可交候选，但完成同步或正式调整 Contract 后才能 DONE。

DONE 必须同时满足：全部适用 Required 和已激活 Conditional 通过且证据有效；执行前有依据确认不适用的 Required 可按第 5 节记录 N/A；交付可复现；知识已更新/无增量；没有必要 BLOCKED；要求客户确认时已经确认。

## 9. 本包的显式实现约定

以下用于补足执行细节，不冒充原文新增要求：

- 包默认任务总修复 4 次、T 为 120 分钟；初始化可覆盖，单任务 Contract 可明确调整。V1.6 原文只规定这两个值必须有限，没有指定 4/120。
- Conditional 在执行前写触发条件；触发后等同 Required，未触发写理由，未知不能当未触发。
- 一次正式“修复 + 重新 Verify”作为一个修复周期，在开始前预占任务计数；涉及的每个根因分别 +1。最后一次获准修复包含其重新验证，但仍受 T 限制。额度只阻止下一次修复，不阻止当前授权周期的验证；T 耗尽须停止新动作并记录未完成检查。本地自检不算正式 Loop，但计入 T。
- `.ai-workflow/project.json` 是项目默认值，任务 Markdown 是该任务事实来源；不同时维护第二套运行状态数据库。
- `check` 只证明安装文件和项目配置结构；`validate-task` 只检查当前任务记录的 schema、状态组合、额度和 Evidence 引用。两者都不能证明业务正确、独立验证真实发生、历史未被篡改或项目能运行。

## 10. 首轮试点

依次选一个可复现 Bug、一个普通功能纵向切片、一次必要跨模块改动。记录交付时间、Human Gate 原因、Loop/Reset 次数、验证缺口、交付后问题/知识复用、流程额外开销。没有观察到就写“未观察”，不填 0 伪装结果。重复痛点出现后才增加工具机制。
